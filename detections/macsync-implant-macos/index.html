MacSync implant and screen-capture helper on macOS

ATT&CK · T1113 (Screen Capture) ATT&CK · T1036.005 (Match Legitimate Name) ATT&CK · T1543.001 (Launch Agent) Tactic · Persistence
Hypothesis. The MacSync stealer leaves two host artefacts that name-based rules miss, a persistent Mach-O implant staged as ~/.local/com.apple.<hex>.hcpi, and an ad-hoc-signed helper that drives the screen-recording grant. Apple ships nothing to ~/.local, so a com.apple-named binary there is a masquerade.

context

This rule is deliberately narrow. The vendor that published the MacSync research already carries broad coverage for it, so this cut is scoped to the few host artefacts that sat outside that coverage. The implant path is the first, because a real Apple component never lands in ~/.local.

The second is the screen-capture helper. It calls CGRequestScreenCaptureAccess to drive the TCC screen-recording grant and drops the .com.apple.tcc.prompted and .com.apple.tcc.result marker files. Validate it against vendor MacSync coverage before deploying so you do not double-alert.

hunt

Match the implant path, the masquerade naming, or the screen-capture grant markers.

// hypothesis: MacSync residual host artefacts on macOS.

FROM logs-edr-process_events
| WHERE host.os.type == "macos"
| WHERE process.command_line LIKE "*/.local/com.apple.*"
     OR process.command_line LIKE "*.hcpi*"
     OR process.command_line LIKE "*CGRequestScreenCaptureAccess*"
     OR process.command_line LIKE "*.com.apple.tcc.result*"
| KEEP host.name, process.parent.name, process.command_line
| SORT @timestamp DESC
| LIMIT 100

findings & discriminators

  • The path is the masquerade. The com.apple name paired with ~/.local is the giveaway, because a genuine Apple component never sits there.
  • Check vendor coverage first. This rule is scoped to fill a gap, so confirm it against existing MacSync detections to avoid duplicate alerting.

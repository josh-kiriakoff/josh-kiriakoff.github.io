unsigned DLL loaded by a system binary from a user path

ATT&CK · T1574.002 (DLL Side-Loading) ATT&CK · T1574.001 (DLL Search Order Hijacking) Tactic · Persistence Tactic · Privilege Escalation
Hypothesis. A trusted binary in System32 or SysWOW64 should resolve its imports from system and vendor directories. An unsigned module pulled in from a user-writable path is a strong search-order hijack or side-load signal, where the planted DLL runs under the identity of the signed host process.

context

The identity transfer is the payoff. Plant a DLL a signed system binary will load and your code inherits that binary's trust, its path, and often its privilege. Search-order hijacking and side-loading both rely on the loader reaching a directory the attacker can write to before it reaches the real one.

The two conditions together are what make the hit strong. A system binary as the loader, and an unsigned module coming from a user path. Either alone is common. Both at once is not.

hunt

Match a System32 or SysWOW64 binary loading an unsigned DLL from a user-writable path.

// hypothesis: signed system binary loading an unsigned DLL from a user path.
// schema:     Huntress Process Insights - library_events (module load)

FROM logs-edr-library_events
| WHERE TO_LOWER(process.executable) LIKE "*\\windows\\system32\\*"
     OR TO_LOWER(process.executable) LIKE "*\\windows\\syswow64\\*"
| WHERE dll.code_signature.signed == false
| WHERE TO_LOWER(dll.path) LIKE "*\\users\\*"
     OR TO_LOWER(dll.path) LIKE "*\\appdata\\*"
     OR TO_LOWER(dll.path) LIKE "*\\temp\\*"
| KEEP host.name, process.executable, dll.path
| SORT @timestamp DESC
| LIMIT 100

findings & discriminators

  • Both conditions carry the weight. The loader being a system binary and the module being unsigned from a user path is the pair that matters. Neither half alone is worth an alert.
  • Baseline the loader. A little in-house software drops unsigned helpers into ProgramData or AppData, so learn the normal loaders before you widen the rule.

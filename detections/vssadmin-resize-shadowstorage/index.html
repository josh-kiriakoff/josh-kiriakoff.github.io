shadow copy eviction via vssadmin resize

ATT&CK · T1490 (Inhibit System Recovery) Tactic · Impact
Hypothesis. Shrinking the shadow-copy storage association to a small maximum size silently evicts existing Volume Shadow Copies without ever issuing a delete. It defeats file restore and recovery while sidestepping detections that only watch for vssadmin delete shadows.

context

This is the quiet path to the same end. Everyone watches for delete shadows, so an operator who resizes the storage instead removes the copies without tripping the obvious rule. The shadow copies fall out because there is no longer room to keep them.

Ransomware crews and hands-on actors both use it as a recovery-inhibition step before or during encryption, which is why a resize to a very small maximum, or one run from a shell mid-intrusion, is worth surfacing.

hunt

Match vssadmin resizing shadow storage.

// hypothesis: vssadmin resize shadowstorage evicting shadow copies.

FROM logs-edr-process_events
| WHERE TO_LOWER(process.name) == "vssadmin.exe"
| WHERE TO_LOWER(process.command_line) LIKE "*resize*"
     AND TO_LOWER(process.command_line) LIKE "*shadowstorage*"
| KEEP host.name, user.name, process.parent.name, process.command_line
| SORT @timestamp DESC
| LIMIT 100

findings & discriminators

  • Resize is the quiet delete. Evicting shadow copies by shrinking their storage reaches the same outcome as a delete while dodging the rule that watches for one.
  • Weigh the size and the context. A resize to a very small maximum, or one run from a shell in an intrusion timeline, is the concern rather than a planned change.
